Semana 6

Fundamentos de ingeniería de datos

Antes de analizar o visualizar datos, alguien tuvo que construir la tubería que los lleva desde su origen hasta un lugar donde se pueden consultar. Esa disciplina es la ingeniería de datos: el trabajo silencioso que hace posible toda la ciencia de datos posterior.

Introducción

Un científico de datos pasa la mayor parte de su tiempo esperando que los datos lleguen limpios, completos y a tiempo. Ese flujo no ocurre por arte de magia: lo diseña y mantiene un ingeniero de datos mediante pipelines. En esta semana aprenderás a pensar como uno: distinguirás ETL de ELT, procesamiento por lotes de flujo continuo, y las tres grandes formas de almacenar datos a escala (data warehouse, data lake y lakehouse). En la segunda sesión bajarás a la práctica: diseñarás un modelo dimensional (esquema estrella) y construirás un pipeline ETL completo en Python que extrae datos, los transforma y los carga a una base de datos SQLite consultable.

Conocimiento previo

Antes de continuar, responde mentalmente: si una tienda en línea genera miles de ventas al día en distintos sistemas (punto de venta, app, sitio web), ¿qué pasos crees que hay que dar para que toda esa información termine en un solo reporte ordenado que la gerencia pueda consultar cada mañana?

Ver una pista para contrastar tu respuesta

Tu lista probablemente incluye: recolectar los datos de cada fuente, limpiarlos y darles un formato común, y guardarlos en un lugar central. Esa secuencia —extraer, transformar, cargar— es exactamente un pipeline ETL, el concepto vertebral de esta semana.

Contenido temático

Sesión 1 · 2 horas

Arquitecturas de datos

Un pipeline de datos es una secuencia de pasos automatizados que mueve datos desde una o varias fuentes hasta un destino, transformándolos en el camino. Es la "tubería" de la organización.

Existen dos grandes formas de ordenar esos pasos:

  • ETL (Extract, Transform, Load): se extraen los datos, se transforman antes de guardarlos, y se cargan ya limpios. Es el enfoque clásico de los data warehouses: los datos llegan al destino listos para usar.
  • ELT (Extract, Load, Transform): se extraen, se cargan crudos al destino, y se transforman después, cuando se necesitan. Es el enfoque moderno del big data, viable cuando el almacenamiento es barato y el poder de cómputo abundante.

Según cuándo se procesan los datos, distinguimos:

  • Batch (por lotes): se procesan grandes volúmenes juntos, en intervalos programados (por ejemplo, el reporte de ventas de todo el día se calcula a medianoche). Eficiente, pero no es en tiempo real.
  • Streaming (flujo continuo): se procesa cada dato en cuanto llega (por ejemplo, detectar un fraude en el instante de la compra). Es en tiempo real, pero más complejo y costoso.

Y según dónde y cómo se almacenan, hay tres arquitecturas:

ArquitecturaQué guardaAnalogía
Data WarehouseDatos estructurados y procesados, en tablas, optimizados para consultas SQL.Una biblioteca con libros catalogados.
Data LakeDatos crudos de cualquier tipo (JSON, texto, imágenes, video). Barato y flexible.Un lago donde se echa todo tal cual llega.
LakehouseHíbrido: la flexibilidad del lake con la estructura y el rendimiento del warehouse.Un lago con un sistema de catalogación encima.
Actividad en clase: en equipos, diseñen en papel un pipeline ETL para un caso de negocio (por ejemplo, una cadena de cafeterías con varias sucursales). Especifiquen las fuentes, las transformaciones, el destino, y justifiquen si conviene ETL o ELT, batch o streaming.
Sesión 2 · 2 horas

Modelado de datos

Guardar datos para analítica no es lo mismo que guardarlos para una aplicación. El modelado dimensional organiza los datos para que las consultas analíticas sean rápidas e intuitivas. Su forma más común es el esquema estrella:

  • Tabla de hechos (fact table): el centro de la estrella. Guarda las métricas numéricas (ventas, cantidades, precios) y las claves que apuntan a las dimensiones.
  • Tablas de dimensiones: los descriptores que dan contexto (categoría, producto, tiempo, cliente). Cada una se conecta directamente a la tabla de hechos, formando una estrella.

El esquema copo de nieve (snowflake) es una variante donde las dimensiones se normalizan en sub-dimensiones (más tablas). Comparación clave:

CriterioEstrellaCopo de nieve
NormalizaciónDesnormalizadoNormalizado
Número de JOINsMenos (más rápido)Más (más lento)
RedundanciaAlgunaMínima
Uso idealDashboards muy consultadosAhorro de espacio

Esto conecta con un principio fundamental: las bases transaccionales (OLTP, que registran compras) se normalizan para evitar redundancia al escribir; las bases analíticas (OLAP, que analizan ventas) se desnormalizan para leer rápido. Distinto objetivo, distinto diseño.

Actividad en clase: construyan un ETL sencillo en Python que extraiga datos de un archivo, los transforme y los cargue a una base de datos SQLite con un esquema estrella (tabla de hechos + dimensión).

2Práctica en PythonPipeline ETL en VS Code
Entrega en Classroom · Enlace a GitHub + notebook o script

Meta integral: construir un pipeline ETL completo que extraiga datos, los transforme con una feature nueva, los modele en un esquema estrella y los cargue a una base de datos SQLite consultable. Este es el flujo real de un ingeniero de datos.

Instrucciones paso a paso

  1. En VS Code, crea una carpeta para el proyecto y un entorno virtual. Instala las librerías con pip install pandas (sqlite3 ya viene con Python).
  2. Prepara un archivo ventas.csv con columnas: producto, categoria, precio, cantidad (puedes inventar 10-15 filas).
  3. Escribe el script etl.py con las tres fases: extracción, transformación y carga.
  4. Verifica el resultado con una consulta SQL que una la tabla de hechos con la dimensión.
  5. Sube el proyecto a un repositorio de GitHub con un README que explique cada fase.

Código del pipeline (etl.py)

import pandas as pd
import sqlite3

# ===== EXTRACT: leer los datos de la fuente =====
df = pd.read_csv("ventas.csv")
print("Extraídas", len(df), "filas")

# ===== TRANSFORM: limpiar y crear una feature nueva =====
df["total"] = df["precio"] * df["cantidad"]   # ingreso por venta

# Modelado dimensional: esquema estrella
dim_categoria = pd.DataFrame({"categoria": df["categoria"].unique()})
dim_categoria["cat_id"] = range(1, len(dim_categoria) + 1)

fact = df.merge(dim_categoria, on="categoria")
fact_ventas = fact[["producto", "cat_id", "precio", "cantidad", "total"]]

# ===== LOAD: cargar a SQLite =====
conn = sqlite3.connect("almacen.db")
dim_categoria.to_sql("dim_categoria", conn, if_exists="replace", index=False)
fact_ventas.to_sql("fact_ventas", conn, if_exists="replace", index=False)

# ===== Consulta analítica (esquema estrella en acción) =====
query = """
SELECT d.categoria, COUNT(*) AS num_ventas, SUM(f.total) AS ingresos
FROM fact_ventas f
JOIN dim_categoria d ON f.cat_id = d.cat_id
GROUP BY d.categoria
ORDER BY ingresos DESC
"""
print(pd.read_sql(query, conn))
conn.close()

  • README que documente qué hace cada fase (EXTRACT, TRANSFORM, LOAD) y qué modela el esquema estrella.

Semana 7

Bases de datos NoSQL y distribuidas

Durante décadas, "base de datos" significó tablas relacionales y SQL. Pero la escala de internet rompió ese molde: cuando los datos son enormes, cambiantes y deben responder en milisegundos a millones de usuarios, surgen nuevas formas de almacenar y distribuir la información. Bienvenido al mundo NoSQL.

Introducción

Las bases relacionales son excelentes para datos estructurados y transacciones consistentes, pero tienen límites cuando se necesita escalar horizontalmente a través de muchos servidores o manejar datos sin un esquema fijo. Las bases NoSQL ("Not Only SQL") responden a esos retos con modelos distintos: documentales, clave-valor, columnares y de grafos. En esta semana entenderás el teorema CAP, que explica por qué ninguna base distribuida puede tenerlo todo, aprenderás cuándo elegir NoSQL sobre SQL, y practicarás operaciones CRUD en MongoDB. En la segunda sesión explorarás cómo estas bases se distribuyen mediante particionamiento y replicación, y compararás en la práctica un mismo problema resuelto con SQL y con NoSQL.

Conocimiento previo

Antes de continuar, responde mentalmente: si tuvieras que guardar el perfil de cada usuario de una red social —donde unos tienen 2 fotos y otros 2000, unos llenan 50 campos y otros solo 3—, ¿te resultaría cómodo hacerlo en una tabla con columnas fijas? ¿Qué problema aparece?

Ver una pista para contrastar tu respuesta

Una tabla rígida obligaría a dejar muchas columnas vacías o a crear tablas auxiliares interminables. Una base documental como MongoDB permite que cada usuario sea un documento flexible con solo los campos que necesita. Esa flexibilidad de esquema es una de las grandes ventajas de NoSQL que verás esta semana.

Contenido temático

Sesión 1 · 2 horas

Modelos NoSQL

El teorema CAP establece que un sistema de datos distribuido no puede garantizar simultáneamente las tres propiedades siguientes; debe sacrificar una:

  • Consistencia (Consistency): todos los nodos ven los mismos datos al mismo tiempo.
  • Disponibilidad (Availability): cada petición recibe una respuesta, aunque no sea la más reciente.
  • Tolerancia a particiones (Partition tolerance): el sistema sigue funcionando aunque se pierda la comunicación entre nodos.

Como las particiones de red son inevitables en un sistema distribuido, en la práctica se elige entre consistencia y disponibilidad. Las bases SQL suelen priorizar consistencia (CP); muchas NoSQL priorizan disponibilidad (AP).

Los cuatro tipos de bases NoSQL y sus casos de uso:

TipoCómo guardaCaso de uso típicoEjemplo
DocumentalDocumentos tipo JSON, flexiblesCatálogos, perfiles, contenidoMongoDB
Clave-valorPares clave → valor, muy rápidoCaché, sesiones, carritosRedis
ColumnarPor columnas, para grandes volúmenesSeries temporales, big dataCassandra
GrafosNodos y relacionesRedes sociales, recomendacionesNeo4j

MongoDB, como ejemplo documental, guarda los datos en colecciones de documentos (similares a objetos JSON). Las operaciones básicas se conocen como CRUD: Create (insertar), Read (consultar), Update (actualizar) y Delete (borrar).

Actividad en clase: modelen una colección en MongoDB (por ejemplo, un catálogo de productos) y realicen las cuatro operaciones CRUD, además de una consulta con filtros.
Sesión 2 · 2 horas

Bases de datos distribuidas

Cuando los datos no caben en un solo servidor o se necesita alta disponibilidad, las bases se distribuyen entre varias máquinas mediante dos técnicas complementarias:

  • Particionamiento (sharding): los datos se dividen en fragmentos (shards) repartidos entre distintos servidores. Cada servidor guarda solo una parte, lo que permite escalar horizontalmente. Por ejemplo, los usuarios A-M en un servidor y N-Z en otro.
  • Replicación: se hacen copias de los datos en varios nodos. Si un nodo falla, otro responde. Mejora la disponibilidad y la tolerancia a fallos.

La consistencia eventual es un modelo común en sistemas distribuidos AP: tras una escritura, los distintos nodos pueden mostrar temporalmente datos distintos, pero eventualmente todos convergen al mismo valor. Es un compromiso: se acepta una breve inconsistencia a cambio de disponibilidad y rapidez.

Dos ejemplos representativos:

  • Cassandra: base columnar distribuida, diseñada para escribir enormes volúmenes con alta disponibilidad y sin un punto único de falla.
  • Redis: base clave-valor en memoria, extremadamente rápida, ideal para caché, sesiones y datos temporales.
Actividad en clase: resuelvan un mismo problema (por ejemplo, almacenar y consultar productos) con un enfoque SQL y con uno NoSQL, y comparen las ventajas y desventajas de cada uno.

2Práctica en PythonCRUD en MongoDB desde VS Code
Entrega en Classroom · Enlace a GitHub + script

Meta integral: modelar una colección documental y realizar las cuatro operaciones CRUD más una agregación, conectándote a MongoDB desde Python. Practicarás el modelo documental de forma integral.

Opciones de conexión

  • Opción A (nube, recomendada): crea una cuenta gratuita en MongoDB Atlas, genera un clúster gratuito y copia la cadena de conexión.
  • Opción B (sin instalar nada): usa mongomock, que simula MongoDB en memoria. Ideal para practicar la sintaxis sin servidor.

Instrucciones paso a paso

  1. En VS Code, crea un entorno virtual e instala el conector: pip install pymongo (y mongomock si eliges la Opción B).
  2. Conéctate a la base de datos y crea una colección productos.
  3. Realiza las cuatro operaciones CRUD: insertar varios documentos, consultar con filtros, actualizar uno y borrar otro.
  4. Ejecuta una agregación (equivalente al GROUP BY de SQL) para resumir por categoría.
  5. Sube el script a GitHub con un README que explique cada operación.

Código (crud_mongo.py)

# Opción B (sin servidor): descomenta estas dos líneas y comenta la conexión real
# import mongomock
# client = mongomock.MongoClient()

from pymongo import MongoClient
client = MongoClient("mongodb://localhost:27017/")   # o tu cadena de Atlas

db = client["tienda"]
productos = db["productos"]
productos.delete_many({})   # limpiar antes de empezar

# ===== CREATE: insertar documentos (flexibles, tipo JSON) =====
productos.insert_many([
    {"nombre": "Laptop", "categoria": "Cómputo", "precio": 15000, "tags": ["portátil", "trabajo"]},
    {"nombre": "Mouse",  "categoria": "Cómputo", "precio": 250,   "tags": ["accesorio"]},
    {"nombre": "Silla",  "categoria": "Oficina", "precio": 1800,  "tags": ["ergonómica"]},
])
print("CREATE — documentos:", productos.count_documents({}))

# ===== READ: consultar con filtros (categoría Cómputo y precio > 200) =====
for d in productos.find({"categoria": "Cómputo", "precio": {"$gt": 200}}):
    print("READ:", d["nombre"], "-", d["precio"])

# ===== UPDATE: actualizar el precio del Mouse =====
productos.update_one({"nombre": "Mouse"}, {"$set": {"precio": 300}})

# ===== DELETE: borrar la Silla =====
productos.delete_one({"nombre": "Silla"})
print("Tras UPDATE y DELETE, quedan:", productos.count_documents({}))

# ===== Agregación: total por categoría (equivalente a GROUP BY) =====
pipeline = [{"$group": {"_id": "$categoria",
                        "total": {"$sum": "$precio"},
                        "n": {"$sum": 1}}}]
print("Agregación:", list(productos.aggregate(pipeline)))

Criterios de entrega

  • Enlace público al repositorio de GitHub con el script.
  • README que explique qué hace cada operación CRUD y cómo se conecta a MongoDB.
  • Salida del programa mostrando las cuatro operaciones y la agregación funcionando.
